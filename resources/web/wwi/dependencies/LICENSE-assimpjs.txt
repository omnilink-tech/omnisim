Licence and provenance notice for assimpjs.js and assimpjs.wasm
==============================================================

This notice accompanies two files in this directory:

    assimpjs.js     136,519 bytes  Emscripten JavaScript loader/wrapper
    assimpjs.wasm 2,442,173 bytes  WebAssembly build of the Open Asset Import
                                   Library plus the assimpjs C++ wrapper

Neither file carries an embedded licence header or copyright notice of its
own: assimpjs.js contains no "Copyright", no @license annotation and no /*!
banner, and the .wasm is symbol-stripped. THREE separately-licensed bodies of
work are combined in them, and this file supplies the notice each one
requires.

The files themselves are byte-unmodified. Nothing here changes them; this is a
notice added beside them.


-------------------------------------------------------------------------
Which upstream these files are, exactly
-------------------------------------------------------------------------

They are cyberbotics/assimpjs -- a FORK of kovacsv/assimpjs -- not upstream
assimpjs. That is established by byte identity, not inferred:

    assimpjs.js    sha256 d63a8621f33f7f93fc46d34fec030bdca8d0965c5b8be160af0d5aea46ff2962
    assimpjs.wasm  sha256 f8cd7de021e5965d62759aaaee7d6ec0a11ecb471d896d0a7195d94990c1fa73

Both match https://github.com/cyberbotics/assimpjs at `main`, path `dist/`,
exactly, and match the same two paths in cyberbotics/webots at `master`,
`develop`, `R2023b` and `R2025a`.

NO kovacsv/assimpjs RELEASE MATCHES EITHER SIZE. All ten upstream releases
ship a .wasm between 3.88 MB and 4.18 MB against our 2.44 MB, because the fork
disables most importers -- "Disable a lot of format to keep only the four that
we support in Webots: obj, dae, stl, fbx", per the fork's own README.

The fork was created 2022-05-06 and reached Webots through
cyberbotics/webots#4519 ("Enhancement assimp webotsjs", merged 2022-05-25),
whose description reads: "Compile Assimp with Emscripten and build some
wrappers to be able to use it in JS (made thanks to
https://github.com/cyberbotics/assimpjs)."

Corroborating evidence inside our own bytes:

  * The .wasm carries the assimpjs project's own C++ class names --
    FileList, FileListIOSystemReadAdapter, FileListIOSystemWriteAdapter,
    FileLoaderEmscripten, ConvertFileEmscripten.

  * ../MeshLoader.js drives exactly the assimpjs API: new ajs.FileList(),
    AddFile(), ConvertFileList(), IsSuccess(), FileCount(), GetFile(0),
    GetContent(), GetErrorCode().

  * THE TELL THAT IT IS THE FORK AND NOT UPSTREAM: ../MeshLoader.js:67 calls
    ConvertFileList(fileList, 'assjson', true) with a THIRD argument.
    Upstream's signature has only ever taken two --
    ConvertFileList(const FileList&, const std::string&). The third parameter,
    `const bool isMesh`, was added in the fork by commit 6e9725f56e ("change
    flags", 2022-05-06, Benjamin Deleze / Cyberbotics) to select which assimp
    components are stripped for a Mesh node versus a CadShape node.

THE FORK'S LICENSE.md IS UPSTREAM'S, UNCHANGED: MIT, Copyright (c) 2021 Viktor
Kovacs. Cyberbotics added no copyright line of their own, so the wrapper
notice below is the one that has to travel.

Layer 3 -- the Emscripten runtime glue: MIT / University of Illinois NCSA
-------------------------------------------------------------------------

assimpjs.js is not hand-written. It is Emscripten's generated module loader,
and a substantial part of its bytes are Emscripten's OWN RUNTIME LIBRARY
compiled into the output -- neither Viktor Kovacs' code nor assimp's, and
covered by neither notice above. Some of the same code is linked into the
.wasm.

The evidence is the runtime's own internal names, present verbatim in the
file: ENVIRONMENT_IS_WEB, wasmBinaryFile, instantiateAsync, getBinaryPromise,
createWasm, keepRuntimeAlive, logExceptionOnExit, requireNodeFS,
readyPromiseResolve, UTF8ArrayToString, writeAsciiToMemory, the embind layer
(__embind_register*, fromWireType / toWireType, BindingError, InternalError),
and the imports emscripten_date_now, emscripten_get_heap_max,
emscripten_memcpy_big, emscripten_realloc_buffer, emscripten_resize_heap,
emscripten_get_now_is_monotonic.

Unresolved
-------------------------------------------------------------------------

  * THE EMSCRIPTEN VERSION IS NOT RECORDED IN THE FILES. No version string is
    embedded. The feature fingerprint -- requireNodeFS and logExceptionOnExit
    both present, arrow functions in use -- places it in the Emscripten 3.1.x
    generation of 2022, and ../wrenjs.js is output of the same generation
    (both carry requireNodeFS, logExceptionOnExit, keepRuntimeAlive,
    instantiateAsync, getBinaryPromise and writeAsciiToMemory). That is an
    inference from which runtime helpers are present, not a version read out
    of the file. The dual MIT/NCSA licence and the copyright line above are
    stable across Emscripten releases.

  * EMSCRIPTEN HAS NO PUBLISHED POSITION ON THE LICENCE OF ITS GENERATED
    OUTPUT. The LICENSE file and the documentation are both silent on it. The
    nearest thing is emscripten-core/emscripten#6824, where the project's
    creator wrote that "The LICENSE file should contain those copyright
    notices, so quoting/linking it should be enough" -- expressly maintainer
    opinion, contested in the same thread by another contributor, and the
    issue was closed by stalebot without any documentation change. This file
    therefore takes the conservative route and reproduces the notice rather
    than relying on that view.

  * THE FORK IS NOT TAGGED OR RELEASED. cyberbotics/assimpjs has no releases
    and no version marker; the artifacts are identified here by sha256 against
    its `main` branch (last pushed 2022-05-19). A future rebuild would be
    distinguishable only by those hashes.
