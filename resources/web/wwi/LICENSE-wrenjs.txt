Licence and provenance notice for wrenjs.js, wrenjs.wasm, wrenjs.data
=====================================================================

This notice accompanies three files in this directory:

    wrenjs.js      202,523 bytes  Emscripten module loader + file-package loader
    wrenjs.wasm    357,135 bytes  WebAssembly build of the WREN renderer
    wrenjs.data    166,631 bytes  Emscripten VFS bundle: 84 GLSL shader files

None of the three carries an embedded licence header or copyright notice.
`wrenjs.wasm` is a fully stripped release build: a byte scan for the strings
"copyright", "licence"/"license", "Cyberbotics", "Webots" and "emscripten"
returns ZERO hits, and it retains no symbol names either (`wr_*` appears only
in the JavaScript export table, not in the binary). This file exists because
three separately-licensed bodies of work are combined in these files and,
until now, none of the three was named in any attribution document in this
repository.

The files themselves are byte-unmodified. Nothing here changes them; this is a
notice added beside them.


-------------------------------------------------------------------------
Where these files came from
-------------------------------------------------------------------------

They were NOT built in this repository. They are prebuilt artifacts fetched
from Cyberbotics' own R2025a web-viewer distribution, vendored so the
streaming viewer does not have to load them from cyberbotics.com at runtime.
The recipe is recorded in this directory's own `.gitignore`, which was turned
into an instructional note by the same change:

    curl -o enum.js     https://cyberbotics.com/wwi/R<rel>/enum.js
    curl -o wrenjs.js   https://cyberbotics.com/wwi/R<rel>/wrenjs.js
    curl -o wrenjs.wasm https://cyberbotics.com/wwi/R<rel>/wrenjs.wasm
    curl -o wrenjs.data https://cyberbotics.com/wwi/R<rel>/wrenjs.data

That matters for attribution, because it means the vendored build contains
**no OmniSim modification**. It is upstream Cyberbotics' R2025a build.

sha256, so a future refresh is distinguishable from these bytes:

    wrenjs.js    deb8dbde9465e90562ef46668d2014b331ede8fb1b1d4ebb6377aa214b79556b
    wrenjs.wasm  72770c92912d47757cf3de7f1447a11d7fba2344aa8e0ef9e9b0bf417e723b56
    wrenjs.data  544350205fd8929d2c5ab6be93ef6b61dc72f9639436b7de32bee3c6371002ae

`enum.js` in this directory came from the same fetch and is the same
Cyberbotics Apache-2.0 material (a table of `WR_*` constants); it is plain
source, not a build artifact, and is covered by the fork derivation recorded
in the repository-root `NOTICE` along with the rest of `resources/web/wwi/`.

-------------------------------------------------------------------------
Layer 2 -- the shaders inside wrenjs.data: Apache-2.0, Cyberbotics Ltd.
-------------------------------------------------------------------------

`wrenjs.data` is an Emscripten file-package containing **84** files, all of
them GLSL under one path prefix (52 `.frag`, 32 `.vert`):

    /resources/wren/shaders/pbr.frag
    /resources/wren/shaders/phong.vert
    /resources/wren/shaders/gtao.frag
    /resources/wren/shaders/smaa_edge_detect.frag
    ... 80 more

The file list is not inferred -- it is read directly out of the package
manifest embedded in `wrenjs.js` (`"filename":"..."` entries). These are
Cyberbotics' WREN shaders and carry WREN's Apache-2.0 licence, Layer 1 above.

!! NOTE: these 84 shaders no longer exist as source in this repository. The
   WREN engine was deleted on 2026-08-23 (commit 976b9449d, "wgpu: D1.4 -- THE
   ATOMIC WREN DELETION"), which removed `resources/wren/shaders/` along with
   `src/wren/`. `resources/wren/LICENSE` was deliberately kept, and the
   shaders now ship ONLY inside this .data blob. That is why they are
   enumerated here: after the deletion, this file is the only place in the
   tree that records what is in that package.

`wrenjs.js` is not hand-written. It is Emscripten's generated module loader,
and a substantial part of its bytes are Emscripten's **own runtime library**
compiled into the output -- not Cyberbotics code and not covered by
Cyberbotics' Apache-2.0 grant.

The evidence is the runtime's own internal names, present verbatim in the
file: `ENVIRONMENT_IS_WEB`, `ENVIRONMENT_IS_PTHREAD`, `wasmBinaryFile`,

-------------------------------------------------------------------------
Unresolved
-------------------------------------------------------------------------

  * THE EMSCRIPTEN VERSION IS NOT RECORDED IN THE FILES. Neither `wrenjs.js`
    nor `wrenjs.wasm` embeds a version string. The feature fingerprint above
    -- `requireNodeFS` and `logExceptionOnExit` both present, arrow functions
    in use -- places it in the Emscripten 3.1.x generation of 2022, but that
    is an inference from which runtime helpers are present, not a version
    read out of the file. The MIT/NCSA dual licence and the copyright line
    above are stable across Emscripten releases; only the exact build is
    unknown.

  * EMSCRIPTEN HAS NO PUBLISHED POSITION ON THE LICENCE OF ITS GENERATED
    OUTPUT. Its LICENSE file and its documentation are both silent on it. The
    nearest thing is emscripten-core/emscripten#6824, where the project's
    creator wrote that "The LICENSE file should contain those copyright
    notices, so quoting/linking it should be enough" -- expressly maintainer
    opinion, contested in the same thread by another contributor, and the
    issue was closed by stalebot without any documentation change. This file
    therefore takes the conservative route and reproduces the notice rather
    than relying on that view.

  * THE WEBOTS RELEASE IS INFERRED FROM THE FETCH RECIPE, NOT FROM THE BYTES.
    The `.gitignore` note and the vendoring change name
    `https://cyberbotics.com/wwi/R2025a/` as the source path. Nothing inside
    the three files states a Webots or WREN version, so a re-fetch from a
    different release would be indistinguishable except by the sha256 above.

  * TWO SHADERS INSIDE wrenjs.data MAY CARRY AN UPSTREAM OBLIGATION THAT
    UPSTREAM NEVER DECLARED, and this is recorded rather than decided.
    `smaa_edge_detect.frag` and `smaa_blending_weights.frag` implement SMAA
    (Enhanced Subpixel Morphological Antialiasing) by Jorge Jimenez et al.,
    reusing its macro vocabulary (`SMAA_THRESHOLD`, `SMAA_MAX_SEARCH_STEPS`,
    `SMAA_AREATEX_MAX_DISTANCE_DIAG`, `SMAAColorEdgeDetection`, ...), and
    `gtao.frag` carries a source comment citing
    `github.com/asylum2010/Asylum_Tutorials`. Neither file carried a
    copyright header in `resources/wren/shaders/` before the deletion, so
    whatever the position is, it is inherited from Cyberbotics and is not
    something this repository introduced or can settle from its own contents.
    Named here so a later reader can find it; NO conclusion is asserted
    either way.
