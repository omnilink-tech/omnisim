# Evidence — the granular subsystem does not support a graded task

**Date:** 2026-08-11
**Machine:** `9722d23d12a3` — host `hc385771a14`, AMD64 16 cores, **NVIDIA
GeForce RTX 3060 Laptop GPU**, driver 596.36, Windows 11
**Binary:** `msys64/mingw64/bin/omnisim-bin.exe`, sha256 `82d5964335feaeaf`,
mtime 2026-08-10, build `e52a1af42`
**Stack:** newton 1.2.0, warp-lang 1.13.0, mujoco 3.8.1, mujoco_warp 3.8.0.3
**Toolchain present on the box:** CUDA 12.1 (`nvcc` at
`C:/Program Files/NVIDIA GPU Computing Toolkit/CUDA/v12.1/bin/nvcc`)

**Purpose.** BuildBench task B2 (`granular_traversal`) proposed grading a robot
crossing, or displacing, a bed of granular material. SPEC 6.1 risk 3 recorded
that "demos exist" is a weaker claim than a scored task. This is the check that
was run before authoring anything.

**Verdict: B2 is not viable. No task was authored.** B2 stays registered at
`BLOCKED` with this record attached (SPEC 7.5 — a blocked task is never
silently deleted).

---

## Method

Each world was run headless as

```
<binary> <world> --batch --mode=fast --no-rendering --minimize
```

from PowerShell (so the engine's embedded interpreter resolves the Newton
runtime), with `OMNISIM_HOME=o:\omnisim` and a unique `OMNISIM_LOG_PATH` per
run, each bounded by a wall-clock kill. None of these worlds contains a
controller that calls `simulationQuit`, so every run was terminated by its
bound; that is expected and does not affect the readings, which come from the
engine's own step log and the `.newton.json` verdict sidecar.

## Run 1 — `tests/cuda/granular_group_load.wbt` (radius 0.02, count 250)

```
INFO: [OmNewtonBackend] warp + newton imports OK; FFI smoke OK
WARNING: GranularGroup is inert: CUDA is not available on this build/box.
         Particles will not simulate; the world remains loadable.
INFO: [OmNewtonBackend] registered 0 dynamic + 5 static Newton bodies
INFO: [OmNewtonBackend] world finalised (solver=MuJoCo (cpu/mj_step, default))
```

Sidecar: `{"backend":"newton","degraded":false,"finalised":true,"solver":"MuJoCo (cpu/mj_step, default)"}`

Body positions were **bit-identical from step 1 to step 61440** — the four walls
and the floor, and nothing else. **Zero dynamic bodies.** The 250 declared
particles contribute nothing to the simulation.

**Finding 1 — particles do not simulate on the shipped binary, and the run still
reports as healthy.** The world loads, Newton finalises, the sidecar says
`degraded: false`. The only signal is one WARNING line. A bare headless PASS
cannot see this.

The box has an RTX 3060 and CUDA 12.1 installed. `OMNISIM_WITH_CUDA`
auto-detects `nvcc` on `PATH` **at build time** (`src/omnisim/Makefile:187-223`);
this binary was built without it. There is **no CPU fallback** —
`allocateDeviceBufferIfPossible` warns once and returns.

Confirmed independently of the log line, so the finding does not rest on a
message the engine chose to print:

```
$ objdump -p msys64/mingw64/bin/omnisim-bin.exe | grep -i "DLL Name" | grep -iE "cud|nvrtc"
   (no matches)
$ strings -n 6 msys64/mingw64/bin/omnisim-bin.exe | grep -cE "^cuLaunchKernel|nvrtcCompileProgram"
0
```

The binary imports **no** `cudart` / `cuda` / `nvrtc` DLL and carries none of
the CUDA driver-API or NVRTC entry points the granular path needs. This is a
CUDA-OFF build in the strongest sense available without rebuilding.

## Run 2 — `tests/cuda/warehouse_husky_granular.wbt` (Husky + 1000 particles, mass 0.5 kg each)

This is the world that most closely resembles B2: a Husky random-walking through
a declared 500 kg granular bed, whose own header comment promises *"the Husky in
turn slows / drifts / stalls when ploughing into the pile"*.

```
WARNING: GranularGroup is inert: CUDA is not available on this build/box.
INFO: [OmNewtonBackend] registered 5 dynamic + 5 static Newton bodies
```

Five dynamic bodies — the Husky chassis and its four wheels. **None of the 1000
particles.** The Husky drives normally (base traverses
(−3.00, −3.00) → (0.34, −1.07) → (−2.02, 1.71) over the run), on bare floor.

**Finding 2 — the flagship robot-in-granular world runs a robot on an empty
floor.** Nothing about traversal, sinkage or traction is being simulated, and
nothing in the run says so beyond the same single WARNING.

## Run 3 — `projects/samples/demos/worlds/physics/granular_sand_demo.wbt`

This world does **not** use `GranularGroup` at all: it is 294 hand-placed rigid
`Solid` spheres (radius 0.05) in a pit whose walls sit at ±1.4 m.
The internal audit `docs/developer/codebase-audit-2026-07.md` §12.6 (not in the
public snapshot) states that since the ODE deletion "the world still loads but the
sand has no physics … the demo shows a frozen pile". That was worth checking rather
than trusting.

```
INFO: [OmNewtonBackend] registered 294 dynamic + 5 static Newton bodies
WARNING: WorldInfo.contactProperties declares coulombFriction 0.65, but this
         world runs on the Newton backend, which does NOT read that field:
         the effective friction is 1.0.
INFO: [OmNewtonBackend] world finalised (solver=MuJoCo (cpu/mj_step, default))
```

| step | t (s) | grain `b5` (x, y, z) |
|---|---|---|
| 1 | 0.03 | (−0.317, −0.319, **1.593**) |
| 30 | 0.96 | (−0.451, −0.541, **0.039**) |
| 240 | 7.7 | (−2.331, −4.929, 0.048) |
| 960 | 30.7 | (−8.783, −19.985, 0.048) |
| 3840 | 122.9 | (**−34.588, −80.210**, 0.048) |

**Finding 3 — the audit doc is wrong: the sand demo is NOT frozen.** 294 dynamic
Newton bodies register and the grains fall from z = 1.593 to z ≈ 0.048 and land.
It never used `GranularGroup`, so the ODE deletion did not freeze it.

**Finding 4 — but it is physically unsound as it stands.** The grains escape a
pit whose walls are at ±1.4 m and roll outward without bound. Between step 960
and step 3840 (92.2 s of sim time) grain `b5` travels 65.2 m — a roughly
constant ≈ 0.71 m·s⁻¹ with no sign of arrest. Other grains read (−70.4, −6.5)
and (+59.7, −53.7) m at the same instant. Whether this is wall tunnelling during
the pile collapse, absent rolling resistance on an infinite ground plane, or
both, is **not diagnosed** — it is reported as observed. The run also uses
μ = 1.0 rather than the authored 0.65, because `WorldInfo.contactProperties` is
the ODE-path friction declaration and Newton does not read it (the engine warns,
correctly).

## Source facts established alongside the runs

These are not repaired by turning CUDA on, which is why the verdict is not
"rebuild with CUDA and retry".

**Blocker A — the robot↔particle collider list is structurally always empty.**
`OmGranularGroup::collectColliders` (`src/omnisim/nodes/OmGranularGroup.cpp`)
skips any Solid for which `solid->body() == NULL`. `OmSolid::body()`
(`src/omnisim/nodes/OmSolid.cpp:1154`) returns the **ODE** body via
`OmSolidMerger`, whose `mBody` is `NULL` in the constructor and never assigned —
there is no `dBodyCreate` left in the tree after `bdc02139`. So `numColliders`
is always 0 and the kernel's collider loop runs zero iterations. **Robots and
particles are mutually invisible — not two-way, not one-way, not at all.**

**Blocker B — the reverse force is written into an empty function.**
`src/omnisim/nodes/OmSolid.cpp:4214-4222`:

> ```
> // Direct body wrenches. ODE removed: OmSolid::addForceAtPosition / addTorque are
> // now UNIMPLEMENTED -- the mouse force/torque drag (OmDragSolidEvent) and the
> // granular-group coupling (OmGranularGroup) that call them apply nothing.
> void OmSolid::addForceAtPosition(const OmVector3 &force, const OmVector3 &position) {
> }
> ```

The working Newton route, `OmSolid::applyExternalForceNewton`, exists and is used
elsewhere — `OmGranularGroup` does not call it.

**Blocker C — there is no particle-state readback.**
`docs/benchmarks/lane4-capability-matrix.md` already records the consequence:

> `object.granular_group` … **PARTIAL** … "GranularGroup parses and appears in
> the scene tree, but this lane has NO way to read particle state through the
> supervisor API, so 'the particles are simulated' is UNMEASURED. Not counted as
> working."

A grader cannot measure displaced mass, or bed-surface deformation, through any
published API.

**Corroboration from the tree's own tracker.**
`docs/developer/granular-cuda-plan.md` states the coupling break independently:

> **Newton coupling — now a HARD BREAK on every world.** … two-way coupling used
> to be *ODE-only*; with ODE gone it is **broken everywhere** … **balls no
> longer push the robot back in any world, and there is no world flag that
> restores it.**

(One inaccuracy in that document, which this check corrects: it adds "One-way
coupling (robot pushes particles) is unaffected." That is wrong — the empty
collider list kills the one-way direction too.)

## Why B2 is not viable

Four independent blockers, any one of which would be sufficient:

1. **Particles do not simulate on the shipped binary** (Run 1, Run 2). Build
   configuration; liftable by a CUDA build.
2. **No robot↔particle coupling in either direction, even with CUDA on**
   (Blocker A). Source fact; not liftable by a build.
3. **The reverse force lands in an empty function** (Blocker B). Source fact.
4. **No particle-state readback, so displaced mass is unmeasurable** (Blocker C).

Both of B2's proposed grading channels are therefore dead: a robot cannot be
affected by the bed (2, 3), and the bed cannot be measured (4).

**The rigid-sphere fallback is not a shortcut.** Run 3 shows bulk rigid spheres
*do* step under Newton, so "N spheres instead of a granular node" is superficially
attractive — but the one such world in the tree contains no robot, and its grains
do not currently behave like granular media (Finding 4). Grading a robot against
that pile would be grading a defect.

**No task was authored.** Inventing a graded task around a subsystem that does
not work is the failure mode BuildBench exists to avoid.

---

## What would change the verdict

- A **CUDA-ON build**, run on this same world set. It would lift blocker 1 and
  turn blocker A from a code reading into a measurement — worth doing, because
  a source reading is weaker evidence than a run, and this record should not be
  the last word on an engine defect.
- Repairing `collectColliders` to enumerate **Newton** bodies, and routing the
  reverse force through `applyExternalForceNewton` (which already exists and
  works). Both are named in `docs/developer/granular-cuda-plan.md` as M3 work.
- A **particle-state readback** on the supervisor or harness surface, without
  which no granular task is gradeable regardless of the physics.

Until then the verdict stands, and it is a statement about the current tree —
**a repairable defect, not an architectural impossibility.** It must never be
quoted as though granular media are beyond the engine.

## Defects found, for the owning workstreams

Recorded here because SPEC 7.4 requires a defect found while building a task to
be published as a defect whether or not the task survives.

1. `docs/developer/codebase-audit-2026-07.md` §12.6 (internal; not in the public
   snapshot) claims the sand demo is frozen. **Measured: it is not** (Finding 3).
   It also mis-describes the demo elsewhere as a Husky traversal.
2. `docs/developer/granular-cuda-plan.md` claims one-way coupling survives.
   **It does not** (Blocker A).
3. `docs/guide/samples-demos.md` describes `granular_sand_demo.wbt` as *"A Husky
   drives across a sandy bed simulated with the granular-media solver."* The
   world contains **no Husky** and does **not** use the granular solver.
4. `granular_sand_demo.wbt` grains escape their pit and roll to ±80 m
   (Finding 4), and the world declares a friction the solver does not read.
5. `tests/benchmarks/omnibench/lane4/worlds/object_granular_group.wbt` authors
   `translation` / `particleCount` / `particleRadius` on a `GranularGroup`;
   **none of those fields exist** (they are `radius` / `count` / `boundsHalfWidth`
   / `mass` / `initialPositions` / `contactMaterial`), so the engine logs
   "Skipped unknown field" and the probe silently instantiates a default group.
