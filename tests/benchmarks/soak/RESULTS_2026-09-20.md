## Drift is linear, and that is the finding

```
closure 0.004 -> 0.722 m over 581 laps

  linear   1.22 mm/lap          rmse 0.0194   <- 5x better
  sqrt(n)  0.0234 * sqrt(lap)   rmse 0.0981
```

Fitted, not eyeballed, and the two models are not close. Linear means a
**systematic** bias — each lap turns fractionally off 90° in the same
direction — rather than a random walk that would grow as √n and stay
roughly bounded in practice.

Extrapolated: **~8.3 m after 24 hours** of laps. The robot would leave any
realistic floor.

So the loop **cannot run unattended for a day** without localisation or a
periodic re-home. This is open-loop dead reckoning; nothing closes the loop
on absolute position, so a sub-degree heading bias integrates forever.

⚠️ **Attribute this correctly.** The drift is in actuation and odometry,
**not interpretation**. A model deciding each of those 4,648 commands would
drift identically — same motors, same physics, same missing feedback. It
says nothing about the deterministic core versus an LLM, and it does not
touch the cost comparison, because both arms inherit it equally. Reading
this as "the cheap path is worse" would be wrong.

Earlier in this session it was twice extrapolated from three or four points,
once as "unbounded ~11 m/day" and once as "decelerating, maybe √n". Both
were premature. That is why the fit is in the tool now.

## The slowdown that wasn't

```
sim-seconds/lap   1st half 188.65   2nd half 184.33   (-2.3%)
wall-seconds/lap  1st half  12.06   2nd half  12.42   (+3.0%)
```

Every lap commands identical motion, so sim-time per lap is fixed by
construction. Flat sim-work with rising wall-clock is host load — and the
host demonstrably was loaded, because a second engine was started mid-run
for the language benchmark.

The raw summary line reads `lap time 1st half 12.1s 2nd half 12.4s`, which
taken alone looks like degradation. It isn't, and **the run before this one
could not have told the difference** — the `sim_s` column was added after a
2-hour run collapsed from 9.2× to 1.8× real-time under Docker/WSL memory
pressure and nearly got reported as an architectural regression.

## What this run cannot tell you

**The leak result is void.** It recorded working set, which Windows trims
on its own: it fell 707 → 191 MB mid-run while private memory held at
~1.3 GB with 17 GB free. Nothing was released. Working set is wrong in both
directions here — it shows a fall where nothing was freed, and would hide a
real leak whose pages were paged out. `private_mb` was added during this
run, so the next one has it; this one has no verdict.
