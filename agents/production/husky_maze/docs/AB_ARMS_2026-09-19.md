# Arm A/B — deterministic solver vs LLM agent (2026-09-19)

**Question:** how much of what the OmniLink agent does on this demo needs a model at
all, and what does removing the model buy? Specifically: does the deterministic arm
match the LLM arm on success, and does it collapse run-to-run variance?

This is also the **re-measurement [RESULTS.md](RESULTS.md) has been owed since
2026-07-19**, when every number on that page was retracted for predating `b18bd7a3`
("wheels-only navigation, no teleport recovery anywhere"). Nothing on this page
shares a run with that one.

Rig: [`scripts/ab_arms.py`](../scripts/ab_arms.py). Raw rows under `../evidence/`.

## What had to be fixed first: the deterministic arm was dead

`solve.py` called `snap_to_cell` at three sites to re-anchor after skid-steer pivots.
`b18bd7a3` removed teleport-snapping **globally** on 2026-05-24 — the action now
answers a deliberate `410 Gone` — and the solver was never migrated with the rest of
the demo. It therefore died on its first pivot, at step 1 of 72, and had done so for
every run since 2026-05-24. Nobody noticed because RESULTS.md was retracted and the
solver was not the product path.

Both sites now use one **synchronous `goto_cell`** per hop, which is what the bridge's
own 410 body names as the replacement: it turns in place under wheel control, drives,
gates the hop against maze adjacency using the husky's *actual settled pose*, and
accepts arrival within half a cell. Nothing teleports. This is also the primitive the
agent arm drives, so the two arms now differ only in **strategy**, not in actuation.

> ⚠️ Anyone re-reading old `solve.py` traces should treat them as teleport-assisted.

### Determinism — the actual result

**The decision layer is bitwise deterministic. The trajectory is not quite.**

- The `goto` decision sequence hashes **identically across all 5 runs**
  (`md5 1a1967889876fb66a4d8fea1e6dc1786`).
- Of 148 trace lines, **9 differ between runs (6%)**, and *every* difference is
  **±0.01 rad in yaw** — one unit in the last printed decimal. Positions agree to
  2 dp; drift agrees exactly; no run took a different route.

The residue is **not** in the policy, it is in the **coupling**. The harness drives the
bridge over HTTP on wall-clock timing while the engine free-runs between calls, so a
settle check samples the pose a tick or two apart from run to run. This is the
documented "there is no pause over HTTP" property showing up as measurement jitter.

**The consequence worth carrying forward:** removing the model does not by itself buy
end-to-end reproducibility. A bitwise-deterministic physics solver plus a fully
deterministic policy still yields a non-identical trace when the two are coupled over
wall-clock HTTP. Closing that last gap requires stepping the controller in lockstep
with the sim clock (in-engine, on `robot.step()`), not over HTTP.

## Arm L — LLM agent: BLOCKED, not measured

Three trials were launched and all failed in ~9 s, before any driving:

```
[chat] using profile 'Husky Maze' (id=6f9ab49b-…) with 28 tools, engine=g1-engine
[chat] turn 1: chat() raised after retries: OmniLinkAPIError:
       OmniLink API error [400]: invalid_grant: Invalid grant: account not found
```

The Omni Key itself is fine — `python -m omnisim key --check` reports **VALID**, plan
*Agent Builder*, providers **google, xai** connected, and the profile and its 28 tools
load. `g1-engine` is the Google-backed engine, and `invalid_grant: account not found`
is a lapsed grant on that provider connection, upstream of OmniSim.

No LLM-arm number is claimed here. The comparison is **owed, not concluded** — and in
particular nothing on this page says the deterministic arm is as capable as the agent.

[`chat_drive.py`](../scripts/chat_drive.py)'s hardcoded engine is now overridable via
`HUSKY_CHAT_ENGINE` (default unchanged), so the arm can be re-pointed at another
connected provider once the grant is restored:

```bash
HUSKY_CHAT_ENGINE=<engine> python agents/production/husky_maze/scripts/ab_arms.py \
    --arm l --worlds maze --trials 5
```

## What this does and does not establish

**Does:** the deterministic arm solves the known-map maze 5/5 under honest wheel
control, in 46 s, with an identical decision sequence every time; and the last
increment of reproducibility is blocked by HTTP coupling, not by the policy.

**Does not:** say anything about the LLM arm's success rate, cost or variance on the
current bridge; establish variance on `husky_maze_unknown` (n=1 there, a smoke result
only); or say anything about `corners`, `visual` and `blind`, which
are **agent-only structurally** — `solve.py` has no code path for a multi-objective,
vision or tag-only brief. That boundary is the interesting part of the question and it
is untouched here.

## Owed

1. Arm L on `maze`, n≥5, once the provider grant is restored.
2. Arm L on `husky_maze_unknown`, and arm D at n≥5 there (only n=1 so far).
3. An in-engine lockstep arm, to test whether the ±0.01 rad yaw residue disappears.
4. Arm L alone on `corners` / `visual` / `blind`, to price what the model is buying
   where the deterministic arm cannot compete at all.
