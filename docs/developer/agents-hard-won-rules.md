## World extension

**⚠️ THE WORLD EXTENSION IS `.omniworld`. OmniSim READS `.wbt` TOO, FOREVER — but never WRITE one.** The policy is **DUAL-READ, SINGLE-WRITE**, and it is the same shape as the file header, which migrated `#VRML_SIM R2025a utf8` → `#OMNISIM R2025a utf8` while the tokenizer kept accepting both. **Read:** the engine, harness, test suite and every script accept `.omniworld` and `.wbt` interchangeably, indefinitely — there are external users and forks, and a `.wbt` world must keep working. **Write:** every new or generated world gets `.omniworld` — Save/Save As, the new-world wizard, `omniworld generate`, and every `gen_*.py`. The tree migrated **661** of its own worlds; `.wbt` is not deprecated, it is *legacy-accepted*. Why a new extension at all: `.wbt` means "Webots" and the format has genuinely forked — `URDFRobot`, `Cloth`, `SoftBody`, the `omnisim://` URL scheme and every `newton*` field are unloadable in Webots, and `Fluid`/`immersionProperties` now hard-ERROR here. It is a **capability signal, not a rebrand**. ⚠️ **In the engine, never hand-roll `endsWith(".wbt")`** — every extension test goes through [`src/omnisim/core/OmWorldFileFormat.hpp`](../../src/omnisim/core/OmWorldFileFormat.hpp) (`isWorldFile`, `writeExtension`, `nameFilters`, `resolveExisting`); that header is the single funnel, and half a dual-read policy is how you ship a world that opens from the CLI but not the file dialog. In Python, accept both (`endswith((".omniworld", ".wbt"))`) and glob both. ⚠️ **Deliberately NOT migrated, do not "finish the job":** `distribution/` (frozen generated artifacts whose `<world>.wbt.seed.json` sidecars pin a byte-determinism claim), all of `tests/benchmarks/` (agentbench's `freeze_manifest.json` pins SHA256 **by path** and a red freeze test is a release gate; `ladder0/` and `adapters/webots/` are upstream-Webots control arms that real Webots must still load), and two worlds kept as live dual-read proof — `tests/cache/worlds/backwards_compatibility.wbt` and [`projects/samples/demos/worlds/physics/newton_dual_read_legacy.wbt`](../../projects/samples/demos/worlds/physics/newton_dual_read_legacy.wbt). Re-run or extend the migration with `python scripts/dev/migrate_world_extension.py --plan|--apply|--verify` (`--verify` audits that every repo-relative world reference still resolves).

## Drive the harness

**You drive the harness.** It exists so you don't ask the user to reload the sim. Use `POST /world/load` once, then **`POST /world/sync` after authored edits**; it selects a verified live pose batch or a full hot reload automatically. Hit `POST /sim/reset` and `POST /sim/step` directly. Don't kill the `omnisim-bin` the user is watching.

## Light mode

**⚠️ LOAD THE HARNESS WITH `"light": true`, OR IT IS SLOWER THAN THE THING IT REPLACES — and on a cloth world it is unusable.** The harness's pitch is that a live engine skips process start. Measured 2026-08-14 (machine `9722d23d12a3`), in the DEFAULT mode that pitch is simply false: a `POST /world/load` reload of `newton_cloth_drape.omniworld` costs **13.4 s**, against **6.37 s** for just re-running `run-headless --until-finalized` in a fresh process. With `{"light": true}` the same reload is **3.1 s** and the ordering flips. **The flag is not an optimisation you add later; it is how you open the world.** ⚠️ **The cost is NOT the scene's node count — it is (sequential supervisor round-trips) × (engine step time),** because each round-trip is serviced at a step boundary. That is why "small scene, skip the flag" is exactly backwards: measured in default mode, an 8-Husky world (240 nodes) and the cloth world (**10 nodes, 2 solids, and zero contacts**) both cost ~4.7 s for one `GET /sim/contacts`, while a 16-node rigid world costs 126 ms — the cloth world is small *and* slow-stepping, so its few round-trips are individually expensive. ✅ **Largely FIXED 2026-08-14 (`3b952b61d`): the per-step trackers no longer re-walk the scene graph every step** (Solid list, per-solid identity, and the robot-subtree index are cached, invalidated on spawn/delete). Heavy-mode cloth stepping went **2222 → 191 ms/step (11.6×)** and `/sim/contacts` 4932 → 786 ms. Light mode is still ~4× better again (44.1 ms/step), so the rule above stands — it is just no longer the difference between usable and unusable. What light mode buys once you have it: pose-only `POST /world/sync` in **325 ms** (`mode: live_pose`), a structural one in **2818 ms** (`mode: full_reload`), 120 stepped frames in 5297 ms and `POST /sim/reset` in 1571 ms — i.e. watch, rewind and re-watch without ever reloading. The trade is that `/sim/grips` and the `contact.*` / `grip.*` / `joint.limit_hit` events go quiet; when you genuinely need those, load heavy *deliberately* and expect the cost. ⚠️ **`/sim/contacts` is NOT part of that trade — it still answers in light mode.** It is served by `observe.collect_contacts`, which walks the scene per call and never touches the `ContactTracker` that `--light` drops. This line claimed otherwise until 2026-08-15, and it was wrong in the expensive direction: it sent agents to a heavy reload to recover a surface that had not gone anywhere. The harness source says so itself at [`omnisim_harness.py`](../../scripts/harness/omnisim_harness.py) (the comment in its `/sim/contacts` handler: served by `observe.collect_contacts`, never touches `ContactTracker`) — only the tracker-fed surfaces are suppressed.

## Suspect the tool

**⚠️ WHEN AN AGENT DRIVES A ROBOT BADLY, SUSPECT THE TOOL BEFORE THE PROMPT — measure the primitive against ground truth first.** An LLM has no independent access to the world: every belief it holds about what the robot did came from a tool result, so a tool that returns the value it was *asked for* installs a false belief that the agent then reports confidently. Its honesty is bounded above by the tool's honesty and no prompt raises that ceiling. Measured here, model held constant every time: the mobile bridge's `turn` delivered **56.7% of the commanded angle** (reproducible to 4 decimals) while its own source comment said "~−19%" — rewriting the control law took it to **mean |error| 0.44°, max 0.97°, n=8** with no prompt, model or agent-config change (`52f3f6ca`); the swarm showcase went **2/4 → 4/4 within 0.08 m** purely by adding `drive_to_xy`; and the anti-fabrication study found 26% of turns contained a fabrication, every one about the agent's own past actions, with **not one coming from a tool read**. So: motion results carry `{commanded, achieved, error, settled}` and never the argument echoed back (unmeasured is `null`, never a number you did not measure); actions complete before returning or say plainly that they do not; one call does what the agent wants (`drive_to(x,y)`, not `turn` then `drive`) with the tool owning geometry, frame and units; a command arriving while busy is **rejected**, never silently clobbered; and a known error goes in the tool description until it is fixed. Caveats that keep this from becoming dogma — better tools ≠ *more* tools (selection accuracy degrades as the surface grows), and this is proven at the **primitive** level: the task-level lift on `omnilink-bench` is the next measurement and has not been made. Full evidence, external citations and limits: [docs/developer/tool-design-for-agents.md](../../docs/developer/tool-design-for-agents.md); short form is pattern 9 in [agents/AGENT_PATTERNS.md](../../agents/AGENT_PATTERNS.md).

## Never kill engines

**⛔ NEVER KILL AN `omnisim-bin` YOU DID NOT SPAWN — a live engine of another session is not an "orphan".** Measured 2026-08-29: five 15-minute headless epochs of one agent lane died mid-run with exit code 1 and no diagnostic, each at the moment a second lane started a capture; the capture pipeline's `detect_orphan_sim()` listed *every* engine on the host and its refuse-and-tell message said "kill the specific PID(s) and retry" — so the second lane did. `taskkill /F` gives the victim exit code 1 and leaves nothing in its log, which reads exactly like an engine crash and cost an evening of false diagnosis. Running engines coexist by design (§3e); the detector now returns only engines whose parent process is gone (`scripts/capture/render.py`, `detect_live_sims()` keeps the old meaning), and the `taskkill /F /IM omnisim-bin.exe` advice is gone. If a foreign engine blocks you, check its command line (`Get-CimInstance Win32_Process`) and wait, or use your own ports.

## Kinematic props

**Kinematic-only props** (conveyors, tables, fiducial markers): set NO `boundingObject`. Visual only. Dense URDF hulls snag on bounding boxes during sweeps and lock joints — looks like an IK or motor-PID bug.

## Base plus arm

**Robots with a base + arm** (TIAGo, Fetch, similar mobile manipulators): MUST initialize arm + torso to a tucked pose on bridge spawn. Otherwise wheel slip looks like a friction/kinematics bug.

## Sensor 501

**`/robot/<def>/sensor/<name>` returns 501 by design.** OmniSim (like upstream Webots) restricts device APIs to the owning controller — the supervisor can't honestly read sibling-robot sensors. Use `/joints` for kinematic state, or have the user's controller expose what you need.

## Sim state

**`/sim/state` is session metadata plus the sim clock, not scene state.** It carries `sim_time_ms` / `basic_time_step_ms` (best-effort, with `sim_time_source` naming the reason whenever they are null), but for scene state use `/robots`, `/robot/<def>/joints`, `/sim/contacts`.

## Empty contacts

**An empty `/sim/contacts` is still not automatically "nothing is touching" — but on Newton the old sleep excuse is gone.** Newton has **no body sleep**, so `WorldInfo.physicsDisableTime` / `physicsDisableLinearThreshold` / `physicsDisableAngularThreshold` no longer gate anything (they were ODE's auto-disable knobs; the fields still parse so legacy worlds load), and `GET /sim/contacts?wake=1` is a **total no-op — it advances nothing** (measured: `tracking.woken` reports `applied: false`, `steps_advanced: 0`). Stop passing it, but not because it costs anything. Since 2026-08-07 the native contact readback is **on by default**, so a body resting on a floor genuinely reports its contacts. Before that flip every Newton world was contact-blind (measured: 1008 contacts on ODE vs **0** on Newton for the same scene, and `/sim/grips` was structurally dead) — that is history now, but it is why you will find worlds and controllers written as if contacts were unreadable. `OMNISIM_NEWTON_NATIVE_CONTACTS=0` (value-parsed) still turns the readback off, which makes the emptiness meaningless again; do not set it. ⚠️ Two contact surfaces are genuinely still dead on Newton and produce **nothing**: contact **sound** and the contact-points **GUI overlay**. An empty overlay is not evidence.

## Mesh convexified

⚠️ **EVERY TRIANGLE-MESH COLLIDER IS SILENTLY CONVEXIFIED — a bowl, cup, tube, C-channel or room shell is a SOLID LUMP.** Measured 2026-08-15 (machine `9722d23d12a3`, CPU `mj_step`): a ball dropped into a bowl collider whose rim is at z=0.38 and whose cavity floor is at z=0.04 rests at **z = 0.4396** — rim + ball radius, exactly. The cavity does not exist. The mechanism is MuJoCo's, not OmniSim's: `solver_mujoco.py` sends both `GeoType.MESH` and `GeoType.CONVEX_MESH` through the same `spec.add_mesh(...)` → `mjGEOM_MESH`, and MuJoCo compiles every mesh geom through its convex-hull path. **Two consequences.** (1) `add_shape_convex_hull` is a measurable no-op here — hull and mesh produced *identical* rest heights on both a convex and a non-convex collider — so do not ask for it and do not expose it as a knob. (2) If you need a genuinely concave collider, **build it from several convex pieces** (a `Group` boundingObject, plus `newtonCompoundColliders TRUE` — ⚠ that is a **`WorldInfo`** field ([`WorldInfo.wrl:52`](../../resources/nodes/WorldInfo.wrl#L52)), *not* a field of the `Group`; this line implied otherwise until 2026-08-15, and writing it on the `Group` is an undeclared field, which is exactly the ERROR that takes a headless exit code to 1), not from one concave mesh. ⚠️ **AND YOU MUST SET THAT FIELD, BECAUSE THE DEFAULT SILENTLY DROPS EVERY CHILD BUT THE FIRST.** With `newtonCompoundColliders` FALSE (the default) a `Group` boundingObject registers `children[0]` and discards 1..n-1 — ~108 compound objects with ≥2 children across ~77 tracked files are in that state (regex recount 2026-09-01; the original count was 120/91, and the exact figure moves with the counting method), and a shipped `Chair.proto` collides as a floating seat slab with no legs. ✅ Since 2026-08-17 that **warns once per node, naming the owning Solid and the drop count**, so it is findable; the default is deliberately NOT flipped, because the same field also selects the inertia source for every dynamic multi-collider body and flipping it would change their dynamics too. ⚠️ `OMNISIM_NEWTON_COMPOUND_COLLIDERS` **was presence-gated, so `=0` turned it ON** (the `OMNISIM_REQUIRE_NEWTON` trap); it is value-parsed as of the same change, and the collider and inertia branches now share one read so they cannot disagree. newton's `approximate_meshes("coacd")` does restore the cavity (measured **0.1797** vs an analytic 0.1800) but produced **93 hulls in 6.7 s** for one bowl and needs `coacd`/`scipy`/`trimesh`, which are **absent from the vendored runtime** — treat it as unbundled, not available. This also independently explains the "dense URDF hulls snag during sweeps" rule above.

## Cone collider

⛔ **A `Cone` boundingObject would KILL THE WHOLE WORLD, and the node is deliberately not collidable — leave it that way.** `GeoType.CONE` is **absent from `geom_type_mapping`** in newton's MuJoCo converter (MuJoCo has no cone geom), so registering one raises `KeyError(9)` at solver construction and the world gets **no Newton world at all** — the same failure class as a loop-closing `SolidReference`. `OmCone` accordingly has no `isSuitableForInsertionInBoundingObject`, and `OmNodeUtilities::isCollisionDetectedGeometryTypeName` excludes it a second time. A cone is convex, so author it as an `IndexedFaceSet` boundingObject instead and MuJoCo's hull path reproduces it exactly: measured rest **0.2985** against an analytic 0.3000.

## Read the fields

**To check whether something collides at all, read the FIELDS, not the pixels.** `GET /scene/node/<def>` reports `boundingObject` and `physics` presence + summary. A Solid collides **only** through its `boundingObject`; visual `children` geometry is never collidable, and that missing field — not gravity, not the solver — is the usual cause of a body falling through a floor.

## Dropped events

**Watch `dropped_sup` / `dropped_log` on `/sim/events`.** Non-zero means you're polling slower than events arrive — raise `limit` or poll more often.

## Static floors

**STATIC FLOORS / TABLES / WALLS ARE SOLID UNDER NEWTON BY DEFAULT (since 2026-08-07), and contact queries SEE them.** Both defaults flipped together after the evidence phase: statics-off meant a static collider collided with **nothing** (a ball dropped onto a floor whose top is at z=0.55 passed through and settled at **z=0.0996** on the implicit z=0 plane — a surface not in the file; with statics on it rests at **0.6496**, exactly box-top + radius. ⚠️ **That 0.0996 is HISTORY: since 2026-08-12 the implicit plane is added ONLY to substitute for an authored `Plane` collider the MuJoCo converter had to drop**, so on a world whose floor is a `Box` the statics-off revert now makes the body fall for ever instead — re-measured 2026-08-13 on `gravity_rest_height.omniworld`, z=-3.039 at step 240 and **-287.959** at step 1920. `OMNISIM_NEWTON_GROUND_PLANE=1` restores the unconditional plane and the old 0.0996 exactly; `=0` refuses it even for the substitution case. This is a *better* engine — a world declaring no ground now genuinely has none, which is what let `--fail-on-runaway` see the AgentBench C2 fall-through case again — but every pre-2026-08-12 rest height measured under statics-off is now unreproducible without that variable), and contacts-off meant `getContactPoints` returned an empty set indistinguishable from "nothing is touching" (measured before the flip, while ODE still shipped: 1008 contacts on ODE vs **0** on Newton for one scene). Worlds whose floor sits at z=0 were masked by the implicit plane, which is why both survived so long. **Precedence:** `WorldInfo.newtonStatics TRUE` always wins; `OMNISIM_NEWTON_STATICS=0` / `OMNISIM_NEWTON_NATIVE_CONTACTS=0` are the exact-revert hatches, and both **parse their value** (`=0` means OFF — the old presence-gated reads made `=0` mean ON). A world that declares `newtonStatics TRUE` keeps statics even under the hatch, so `=0` reproduces the pre-flip build exactly. Pinned by `tests/test_newton_static_floor_collides.py` and `tests/test_newton_contacts_visible_by_default.py` (5 + 5 cases, incl. a geometric rest-height assertion so an empty contact list can never be excused as "really mid-air").

## Njmax overflow

**⚠️ MORE THAN ~8 WHEELED ROBOTS ON `mujoco_warp`? RAISE `WorldInfo.newtonNjmax` / `newtonNconmax` — the 256 default overflows SILENTLY.** mujoco_warp does not read the MJCF `<size njmax>` tag and its own auto-estimate is far too small, so the engine pins **256** constraint rows / contacts. Measured on a flat-ground 10-Husky world (pyramidal cone): each 4-wheel-drive Husky rests on 8 wheel–ground contacts = **32 constraint rows**, so ten of them peak at `nefc` **320** / `ncon` 80 — over the cap from tick 4. Rule of thumb: **N wheeled robots ≈ 32·N rows**, i.e. 256 runs out at 9. Overflow **truncates the constraint vector and degrades contact solving with no error you will ever see**: its only warning is a `wp.printf` from inside the solver kernel, which floods one line per tick where stdout is captured and is **discarded entirely on Windows**, where `omnisim-bin.exe` is a GUI-subsystem binary. So the symptom is "the physics feels wrong at scale", not a message. Set the per-world fields (`0` = keep the built-in 256, `-1` = newton's own estimate), or `OMNISIM_NEWTON_NJMAX` / `OMNISIM_NEWTON_NCONMAX` to override them; measure the real peak with `OMNISIM_NEWTON_CONSTRAINT_STATS=<sample every N steps>`, which logs observed peak `nefc`/`ncon` against the caps into `.build_tmp/newton_solver.log`. The caps are handed to `SolverMuJoCo` on both the CPU and GPU paths; the **overflow telemetry** is sampled only on `mujoco_warp`, which is also the path where the overflow is silent. Field reference: [docs/reference/worldinfo.md](../../docs/reference/worldinfo.md). ✅ **THE OVERFLOW IS NOW MEASURED, ON TWO MACHINES, AND THE DETECTOR THAT COULD NOT BE MADE TO GO RED HAS GONE RED.** This bullet said for a week that lane 4b's instrument *"does NOT currently reproduce it"* and that `cliff_detector_validated: false` meant nothing could be concluded. Re-swept **2026-08-17** on the current binaries, machines `9722d23d12a3` (RTX 3060 laptop, Windows) and `8ab788c4c833` (RunPod RTX A4500 / EPYC 7352, Linux): peak `nefc` runs **16/32/64/128 at N=1/2/4/8 on BOTH machines**, then **232 (laptop) / 208 (pod) at N=12**, then **336 / 328 at N=16 against a `njmax` that stays pinned at 256** — i.e. a real, silent truncation, with a clean log and exit code 0. Both summary rows now read `cliff_detector_validated: true`. ⚠️ **Two numbers in the paragraph above are therefore narrowed.** (1) The cap does **not** auto-size: the 2026-08-10 sweep where it tracked demand (`384/384` at N=12, `512/512` at N=16) was that older build's behaviour, not the laptop's, and "mujoco_warp will size it for you" is refuted. (2) The rule of thumb on lane 4b's **generated rovers** is **≈16·N up to N=8, super-linear above it, and the cap is crossed at N=16** — not 32·N crossing at 9. The 32·N / ~9-robot figure was measured on the **10-Husky** world, which still has not been run through this instrument, so it is neither confirmed nor refuted; the two worlds simply do not generate the same contact set. Campaign: [docs/benchmarks/lane4-multimachine-2026-08-17.md](../../docs/benchmarks/lane4-multimachine-2026-08-17.md).

## Backend fields

**The backend fields still parse, and every value now runs on Newton — the "`"ode"` = no physics" trap is CLOSED as of 2026-09-02.** ODE was deleted in `bdc02139`; Newton is the only backend. `physicsBackend` (per-`Solid`/`Robot`) and `defaultPhysicsBackend` (world-level) are **still declared in the schema and still accept `"ode"`**, because an *undeclared* field is a parse ERROR that takes a headless run's exit code to 1 and tracked worlds still carry the value. Until 2026-09-02 a Solid pinned to `"ode"` resolved to an inert stub (`OmOdeBackend`, every op returned `-1`) and was **registered with no solver at all** — no gravity, no contacts — while the world loaded clean and only a per-Solid warning said so. That stub layer is gone (`OmPhysicsBackendKind::Ode`, `OmOdeBackend`, `OmSimulationCluster`, `src/omnisim/ode/`): `OmPhysicsBackendRegistry::resolve()` returns Newton for every kind, and `OmSolid::effectivePhysicsBackendName` reads a retired value as `"auto"` and logs **one warning per world** naming the first offender (`physicsBackend "ode" is retired; this Solid runs on Newton, the only backend`). Measured 2026-09-02 on a throwaway world: a 1 kg box pinned to `"ode"` fell from z=2.0 (steps 1/30/60: 1.997 → 0.832 → 0.099) and rested at z=0.10 on the floor with the warning printed exactly once; before the change the same box hung in the air. Consequence to know about: the G1 ghost worlds that pinned their hologram robot to `"ode"` as a "do not simulate this" switch now go through the ordinary `"auto"` path (a collider-less, physics-less link registers nothing with Newton; the wall-clock cost the old header comment claimed for that idiom — t=8721 vs ~9700 in a 900 s budget — has not been re-measured, and if it matters the idiom needs its own field). **Never write `"ode"` into a new world** — leave `physicsBackend` off (the `"auto"` default is Newton) or write `"newton"` when you want it explicit. Still true: writing `physicsBackend` *inside* `WorldInfo` logs `ERROR: … Skipped unknown 'physicsBackend' field in WorldInfo node` and that ERROR takes the headless exit code to 1, so a typo reads as a crash (measured 2026-08-02 — it cost a benchmark run and the diagnosis went to the physics before the field name). The retired env vars went with the stub — `OMNISIM_FORCE_ODE`, `OMNISIM_LEGACY` (physics arm), `OMNISIM_ALLOW_ODE_FALLBACK`, `OMNISIM_NEWTON_SKIP_ODE_PASS`, `OMNISIM_NEWTON_MESH_TO_ODE`, `OMNISIM_NEWTON_CONTACTS_CMP` — a value that used to select nothing now selects nothing silently; `OMNISIM_REQUIRE_NEWTON` stays because it gates a MISSING runtime, which is real.

## Engine defaults

**Engine defaults (v5): Newton/MuJoCo physics and wgpu-native rendering — the ONLY physics and the ONLY renderer.** ODE was deleted in `bdc02139` (2026-08-08, `src/ode` + `include/ode`, 106,283 lines). There is no second solver, no fallback tier, and **no degraded mode to land in**: the Newton Python runtime (`newton` / `warp` / `mujoco`) reachable by the embedded interpreter is now a **hard requirement**, not a capability. A clone without it has no physics at all — that is a broken install, so treat "bodies don't move / nothing falls" as *first* a missing-runtime check (`python -m omnisim doctor`), not a world bug. Because the deletion is this recent, the Newton feature set is what matters now, and four device paths went **native and DEFAULT ON** in `6eb35675` to keep it complete: the **raycast service** (`mj_ray`), answering `DistanceSensor`, `Receiver`, `LightSensor` and — since 2026-08-08 — **`Radar` and Camera-recognition occlusion too**. ⚠️ **RAY SENSORS DO NOT WORK ON `newtonSolver "mujoco_warp"` AND, SINCE 2026-08-17, THEY SAY SO INSTEAD OF LYING.** `raycast_batch` served off `solver.mj_data` **with no CPU/GPU gate**, and newton's `SolverMuJoCo.step()` writes `mj_data` **only** on its `use_mujoco_cpu` branch (`newton/_src/solvers/mujoco/solver_mujoco.py:3831` — ⚠️ a path **inside the vendored Newton runtime bundle, gitignored and in no clone**: Windows stages it at `msys64/mingw64/bin/newton-runtime/site-packages/`, Linux resolves it from the system `python3`) — the warp branch steps `mjw_data` on the device and never touches it, while `mj_data` still *exists* there because `put_data()` seeds the GPU copy from it at build time. So the service did not fail on the GPU; it answered against the scene **as authored at t=0**. ✅ **THE DECISIVE DIFFERENTIAL HAS NOW BEEN RUN** (this line said it had not). One world, laser `DistanceSensor` aimed at a box whose near face starts at exactly 1.0 m and is then released in free fall, read after 0.512 s of sim time — machine `9722d23d12a3`, RTX 3060: **CPU control 10.0** (the box has fallen out of the beam; 10.0 is the lookupTable max, i.e. no hit), **GPU pre-fix 1.0000000447** (a hit at exactly the authored t=0 distance — *the lie*), **GPU guarded 10.0**. The ray's *origin* was never the problem (the engine builds it from its own scene-graph `matrix()`, fresh on both paths), which is why the two older measurements look contradictory and are not: a **moving sensor against a static wall tracks to 2e-05 m** (ladder0 rung 6, 2026-08-12) because a static geom's t=0 pose *is* its pose at every t. **`raycast_batch` and `get_contacts` now carry the same `use_mujoco_cpu` guard `weld_engage` / `touch_force` always had**, so on the GPU solver rays are DECLINED (each consumer keeps its previous verdict) and contacts fall back to newton's own narrow phase — which IS live there, with correct body pairs but support-point positions and depth 0. Both log a one-shot WARNING on first use, engine-side and once per world (not per process); **the runtime cannot log it itself**, because `omnisim-bin.exe` is a GUI-subsystem binary and the embedded interpreter's `print` is discarded on Windows. Exact-revert hatch for A/B only: `OMNISIM_NEWTON_GPU_STALE_READBACK=1` (value-parsed). Full derivation + line references: [docs/guide/newton-physics-backend.md](../../docs/guide/newton-physics-backend.md). Those two share `OmObjectDetection`, whose ray carrier *was* the ODE ray geom; `bdc02139` removed it, leaving `mRayGeoms` permanently empty so `refreshCollisionDepthsFromNewton` returned at `n == 0` and **every** target read as unoccluded. ## Newton sidecar

**Verifying Newton actually drove the world — read the SIDECAR, don't scrape the log.** At finalize the engine writes a race-free backend-verdict sidecar next to its log: `<OMNISIM_LOG_PATH>.newton.json` (default `omnisim_log.txt.newton.json`), containing `{backend, solver, finalised, degraded, runtime}` (commit `17f9d32c`, [`OmNewtonBackend::writeNewtonVerdictSidecar`](../../src/omnisim/physics/OmNewtonBackend.cpp)) — where **`runtime` names the newton / warp / mujoco / mujoco_warp versions AND the model device** that drove the run (added 2026-08-09). That block exists so a measurement is SELF-DESCRIBING: the moment a second runtime version is staged on a machine, results produced by the two become indistinguishable after the fact without it, and `device` is part of what a number means since the CPU-device pin was worth 1.4–2.4×. `OmLog` **deletes any stale copy when it truncates the log at startup**, so the file's mere presence == "Newton drove THIS run". *Fallback only* (no file log, or an older binary): scrape the log for `[OmNewtonBackend] world finalised (solver=...)`. Either way: `[OmNewtonBackend] imports OK` / `FFI smoke OK` only prove the runtime *loaded*, never that it drove the sim; and a short headless run must actually reach world-finalize for the sidecar to exist — budget `--duration ≥15` on a fast local disk, and **≥45 for cold loads on slower or virtualized disks (WSL2, network volumes, cloud pods)**, where 15 s ends before finalize. **A missing sidecar after a too-short run proves nothing** — it means the run never reached finalize. A stock `make release` bundles the Newton runtime **by default** (`BUNDLE_NEWTON ?= 1`, idempotent; opt out `BUNDLE_NEWTON=0` only if you are supplying it yourself) — a from-source clone / `make debug` without the runtime has no physics (fix: `make -C src/omnisim bundle-newton-runtime`, see [docs/developer/newton-runtime-bundle.md](../../docs/developer/newton-runtime-bundle.md)). The bundle is a **Windows** packaging mechanism; **on Linux (verified working, v5.1) the bundler is not involved** — the embedded interpreter resolves the **system** `python3`, so `pip install torch warp-lang newton mujoco mujoco-warp` into the system interpreter (NOT a venv — the embed ignores venvs) is the whole setup. **wgpu is the ONLY renderer — WREN was DELETED on 2026-08-23 (D1.4, commit `976b9449d`: `src/wren` + `include/wren` + `src/omnisim/wren` + the WREN shader tree, ~31k lines).** The main view (default since 2026-08-19) AND every Camera/RangeFinder/Lidar device render through wgpu; every camera-family device sets up wrenless and renders offscreen, so camera images work windowed, `--minimize`, under `OMNISIM_NO_WINDOW=1`, and with no GL context at all. `renderBackend "wren"` (and `WorldInfo.defaultRenderBackend "wren"`) still PARSES — an undeclared field would be a hard ERROR — but it is a warned no-op that renders wgpu (F1); `OMNISIM_FORCE_WREN` / `OMNISIM_LEGACY`'s render arm are equally warned no-ops. **A host whose wgpu-native cannot initialise now has NO renderer** (one loud log line; physics/controllers unaffected) — there is no fallback tier (R8, owner-assumed 2026-08-22). **⚠️ ROS 2 SHIPS — the "declared NON-GOAL" line this bullet used to carry was REVERSED on 2026-08-17, so do not answer from an older session's memory.** OmniSim implements the ROS 2 [`simulation_interfaces`](https://github.com/ros-simulation/simulation_interfaces) standard (v2.1.0) — the same one Gazebo, Isaac Sim and O3DE implement — plus a live robot surface, as a **sidecar package** at [`packages/omnisim-ros2/`](../../packages/omnisim-ros2/). **Tier 1** is 15 services + the `SimulateSteps` action, each mapped onto a harness endpoint that already existed. **Tier 2** is `/clock` (with `use_sim_time`), `/tf` + `/tf_static` as a real tree, `<robot>/joint_states`, `nav_msgs/Odometry` on `/odom`, `cmd_vel` + `joint_command`, and — since 2026-08-17 — **sensor topics** (`sensor_msgs/Imu` on `/imu/data`, `LaserScan` on `/scan`, GPS on `/gps/local`), all **onto the robot's own bridge, never the harness** — the supervisor can teleport a body but cannot drive a motor or read a device it does not own, which is the same reason `GET /robot/<def>/sensor/<name>` is a 501. ⚠️ **THE SENSOR LANE HAS THREE TRAPS THAT ARE NOT GUESSABLE, and two of them are engine-side.** (1) **A URDF robot has ZERO devices unless the world was loaded with `OMNISIM_URDF_USE_SENSORS=1`** — the importer parses `<gazebo>` sensor blocks always and DROPS them at emit time when that is unset (measured on the shipped Husky: **0 devices without it, 5 with it**), so "no sensors" is almost always this and not a robot that carries nothing. ⚠️ That gate's own source comment says the emission path "crashes OmniSim' device registration mid-startup" — **that comment is STALE**: it loads cleanly and the devices work. (2) ✅ **FIXED 2026-09-01 (`bde550489`): `Gyro` and `Accelerometer` now read their FOLDED CARRIER's body** — the defect was never the devices or a URDF artefact: both read `bodyHandle()`, which is non-null only when the exact carrier Solid owns a Newton body, and the importer's nested IMU carrier owns none (the registration fold welds it into its leader). They now resolve via the new `carrierBodyHandle()` (the ancestor-walking read welds already used); lane 4's `device.imu_nested_carrier` probe — the importer's exact emission pattern, with a direct-mount in-run control — measures both devices `works`, and a body-less Accelerometer publishes gravity-only with a latched warning instead of NaN. ✅ `omnisim_ros2` was re-pointed the same day (`64a083d65`): `covariance[0] = 0.0` when a message's field came from exactly three finite device floats, `-1` kept for absent/warming/non-finite — code-verified against the engine fix; live ROS-stack verification is still owed by the WSL bringup lane. Historical symptom (pre-fix): Gyro constant `[0,0,0]` while demonstrably rotating, Accelerometer no sample at all — not even gravity — while the `InertialUnit` in the *same* carrier Solid tracked yaw to 4 decimals (`+0.1300` vs the supervisor's `0.1300`). So the defect is device-type-specific, not a URDF-import artefact, and `sensor_msgs/Imu` ships a real orientation with `angular_velocity_covariance[0]` and `linear_acceleration_covariance[0]` set to **`-1`** (the ROS convention for "not available") rather than zeros a consumer would read as measurements. The genuine yaw rate is on `/odom`, differenced from pose. (3) **`LaserScan` is single-layer but OmniSim's `Lidar` node defaults to `numberOfLayers 4`**, and the importer only writes that field when the URDF asks for >1 — so a URDF-declared *planar* scanner still arrives 4-layer, and whole layers can be empty (measured `[0, 0, 0, 541]`). Only `omnilink_mobile_bridge` implements `/read_sensor` + `/list_sensors`; every other bridge has none, so read `capabilities.sensors` rather than assuming the verb. **Tier 3** is a `hardware_interface::SystemInterface` (`omnisim_ros2_control/OmniSimSystem`, C++/ament_cmake), so `controller_manager` treats an OmniSim robot as ordinary hardware — state from the harness's `GET /robot/<def>/joints`, commands to the robot's own bridge, no new OmniSim surface and no engine change. ✅ **Verified for a velocity-commanded base**: `diff_drive_controller` + `joint_state_broadcaster` on the Husky, which drove from `x = −0.00000` to `x = +5.59211` — **5.5921 m over 195.22 s of simulated time**, pose and clock read out of the simulator rather than echoed from the command — and an A/B against a direct `POST /set_velocity` control arm with ROS removed entirely agrees within ~4%, so the 12–25% shortfall against the commanded speed is the robot and its bridge, not the ROS layer. ⛔ **MoveIt is UNBLOCKED but NOT brought up — the arm-bridge blocker was fixed 2026-08-19.** `omnilink_arm_bridge` treats a joint command as a GOAL (still measured true: a second `set_joint_positions` 50 ms after the first comes back `HTTP 409 accepted=False error='busy'` and is NOT applied — a trajectory controller pointing at that verb lands **in pieces**), but it now also serves the non-blocking, superseding servo lane a trajectory controller needs: **`POST /servo_joint_positions`** (PROTOCOL.md §6.1) — last-write-wins, never a 409 for servo-on-servo, preempts an in-flight goal and names it in `preempted`, measured result parks into `get_robot_state.last_command`. Verified on `omnilink_ur5e.omniworld`: 24 setpoints at ~18 Hz, 24/24 accepted, zero 409s, parked max error 0.011 rad. The ROS-side wiring is done too (same day): `joint_command` (Tier 2) and `command_mode: joint_positions` (Tier 3) select the verb from the bridge's `/capabilities` — servo when `capabilities.servo` is advertised, goal verb (with the 409-explainer, demoted to that lane) otherwise — live-verified on Tier 2 via WSL Humble (60 messages at 15 Hz, zero 409s, settled 0.018 rad from target). Still open: Tier 3's servo path has not run under a live `controller_manager`, and MoveIt has never been brought up end-to-end — "unblocked", never "working". ✅ **Nav2 has been brought up against OmniSim (2026-08-31, ROS 2 Jazzy)** — a full Nav2 stack drove the Husky to a `NavigateToPose` goal, but scope it exactly: **planning + goal execution ONLY**, on the all-in-WSL Ubuntu 24.04 path (rolling costmap, no `static_layer`, `lidar_layer:=0` on a short-wall test world), **not** a localization or obstacle-avoidance benchmark. Ships as the standalone `ament_python` package [`packages/omnisim-ros2/src/omnisim_ros2_nav2/`](../../packages/omnisim-ros2/src/omnisim_ros2_nav2/) (runbook + beta-feedback REPORT), layered on the Tier-2 sidecar with no new OmniSim surface. OmniSim is still absent from the `ros2_control` simulator registry. ⚠️ **`update_rate` is NOT the actuation rate**: `read()`/`write()` do no I/O (a mutex-guarded copy, safe at any rate) and one background thread owns the HTTP at `comms_rate_hz`. **The ceiling is OmniSim's supervisor round trip, not TCP** — measured on machine `9722d23d12a3`, `GET /robot/<def>/joints` costs **21.01 ms** against **4.48 ms** for a bare `GET /healthz` on the same server, so a read+write cycle is ~22 ms and the hard ceiling is near **45 Hz**; the shipped default is 25 Hz. **THE ENGINE STAYS ROS-FREE and that constraint is not negotiable:** no `rclcpp` in `src/omnisim/`, no ROS in the engine Makefiles, and a non-ROS user's build is unaffected. HTTP/JSON ([PROTOCOL.md](../../PROTOCOL.md)) remains the first-class agent interface; ROS is *additive*, layered on top of it. ⚠️ Four measured traps live in that package's README and are not guessable: the harness runs worlds at **13.24× realtime** (measured, machine `9722d23d12a3`) — ✅ since public issue #13 the harness accepts `--engine-mode realtime` / `OMNISIM_HARNESS_ENGINE_MODE=realtime` (measured: 1.00× wall pacing vs 12.51× default), which is what sensor-driven ROS 2 stacks (Nav2 / slam_toolbox) need — but in the DEFAULT fast mode a wall-clock `cmd_vel` duration is **not** a distance and `get_clock()` under `use_sim_time` is the wrong clock for a watchdog — ⚠️ **and the Tier 3 form of that trap is worse, because it is SILENT: `diff_drive_controller`'s `cmd_vel_timeout` is evaluated on the SIMULATION clock**, so the stock 0.5 s expires between consecutive messages from a 20 Hz *wall-clock* publisher. Measured: the Husky moved **0.0000 m** against a commanded 0.2 m/s while `/diff_drive_controller/cmd_vel_out` published all zeros, the controller reported no error, the hardware plugin reported 0 failures at its full rate, and the only way to see it was to read the robot's pose out of the simulator (the shipped config uses 2.0 s and explains how to scale it). ⚠️ **A fourth trap bit the measurement itself: never read the simulation clock and a pose from two DIFFERENT harness calls.** `GET /sim/state` and `GET /robots` are two supervisor RPCs serviced at different engine step boundaries, and under `--mode=fast` the gap between them is seconds of simulated time and moves with HTTP load — the same 10-second drive read **+50.6%** and **−21.8%** of its commanded speed depending only on how busy the harness was, and both were artefacts. Take the clock and the pose from one response, and remember that **a wheel cannot exceed its own velocity setpoint**: an achieved value that beats its command is a bad denominator, not a fast robot. ✅ **the HARNESS speaks HTTP/1.1 WITH keep-alive as of 2026-09-01** — this line used to warn it was HTTP/1.0 and that every harness-facing publish tick cost a TCP connection (a 50 Hz bringup exhausted Windows' 16,384-port ephemeral range: 17,487 sockets in `TIME_WAIT`, surfacing as `WinError 10048`, which reads like a bind conflict but is exhaustion). Measured on the flip (machine `9722d23d12a3`, 229 requests): connection reuse 0/229 → 229/229, `TIME_WAIT` growth +221 → +6, `GET /healthz` 5.09 → 0.31 ms (196 → 3222 req/s). The BRIDGE already spoke HTTP/1.1 and the ROS client already pools (its earlier A/B: +300 `TIME_WAIT` at 114.8 req/s → +0 at 908.8 req/s, 7.9×); the pool's HTTP/1.0-peer detection now simply never fires against the harness. The same 2026-09-01 change also fixed the deeper supervisor-read cost the 45 Hz ceiling above was computed from (the engine now serves a controller's immediate-request burst at pipe speed instead of one event-loop wakeup each — measured 7.4 → 0.6 ms/read on the 309-node fleet arena, `GET /debug/read_bench` measures it on any live session), so re-derive that ceiling before trusting it. `OMNISIM_ROS2_KEEPALIVE=0` reverts the client for an A/B. And `EntityState.twist` is returned as **zeros because it is UNMEASURED**, never because the body is at rest.
