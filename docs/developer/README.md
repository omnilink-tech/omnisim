# OmniSim Developer Docs

This directory is the implementation-facing documentation set for OmniSim contributors. It is meant to be read while changing code, validating a fix, or planning subsystem work.

> ## ⚠️ WREN IS DELETED (2026-08-23) — READ THIS BEFORE TRUSTING ANY RENDERING DOC HERE
>
> `976b9449d` deleted the WREN renderer (`src/wren/`, `include/wren/`, `src/omnisim/wren/` and 86 shaders). **wgpu-native is the only renderer** — for the main view and for every `Camera`, `RangeFinder` and `Lidar` device, which now render offscreen and therefore work windowed, minimised, under `OMNISIM_NO_WINDOW=1`, and with no GL context at all.
>
> **There is no fallback renderer.** `renderBackend "wren"` and `WorldInfo.defaultRenderBackend "wren"` still PARSE — an undeclared field is a hard load ERROR, so they had to — but they are **warned no-ops that render wgpu anyway**, as are `OMNISIM_FORCE_WREN` and `OMNISIM_LEGACY`'s render arm. A host whose wgpu-native cannot initialise now has **no renderer at all**: one loud log line, and physics and controllers carry on unaffected.
>
> Read every "WREN remains canonical / is the default / is the fallback" line in this docs set the way the ODE banner below asks you to read its equivalents — **as a record of the migration while it was running, not as a description of the machine.** The migration *plans* (`engine-migration-plan.md`, `default-flip-plan.md`, `architectural-baseline.md`) are the clearest cases: they are dated working documents and their mid-flight statements were true when written. The current-state reference is [`wgpu-renderer-status.md`](wgpu-renderer-status.md).
>
> What survives of WREN, and is not a mistake: `resources/wren/` (ten Cyberbotics gizmo meshes and overlay textures the wgpu GUI still reads), the frozen reference images at `tests/rendering/wren_reference/`, and the separately-vendored `wrenjs` build behind the `--stream` browser viewer, which is independent of the engine deletion and **permanently diverges in look** from the desktop view — recorded and accepted.

> ## ⚠️ ODE IS DELETED (2026-08-08) — READ THIS BEFORE TRUSTING ANY PHYSICS DOC HERE
>
> `bdc02139` deleted the vendored ODE library (`src/ode/`, `include/ode/`, 106,283 lines). **Newton with `SolverMuJoCo` is the only physics backend**, in a CPU (`mj_step`) and a batched-GPU (`mujoco_warp`) profile. XPBD was removed too (`94f04222`), the physics-plugin C ABI was deleted (`a0ed801c`), and so was the `Fluid` node (`f0574cbe`).
>
> **There is no fallback backend.** `OMNISIM_FORCE_ODE`, `OMNISIM_LEGACY`, `OMNISIM_ALLOW_ODE_FALLBACK`, `physicsBackend "ode"` and `defaultPhysicsBackend "ode"` no longer select a working backend. Anywhere in this docs set that says "falls back to ODE", "silently runs ODE", "ODE is the fallback", or "both backends" is describing a machine that no longer exists. Many pages carry dated correction banners; some do not yet.
>
> 🔴 **But "no ODE" is NOT the same as "asking for ODE fails loudly" — verified in source, and this is the trap to know.** A world that still pins `physicsBackend "ode"` **loads fine and runs with no physics at all, silently**: `OmSolid::effectivePhysicsBackendName` treats an explicit `"ode"` as a choice that always wins, and hands the Solid an inert stub. (Refusing these at construction was tried and reverted — it wrongly refused 4 of 4 `defaultPhysicsBackend "ode"` worlds.) The same silent-stub path is taken by a clone where the **Newton runtime is simply absent**; only an *installed-but-broken* runtime is refused with a FATAL. Consequence: **set `OMNISIM_REQUIRE_NEWTON=1` on any deploy, CI or benchmark run whose result you intend to trust**, and prove Newton drove a world by asserting the `.newton.json` sidecar — never by exit code and never by a tail-scraped log line.
>
> **Three consequences that change how you read the evidence here:**
>
> 1. **There is no second IN-ENGINE path to cross-check the plumbing.** Note the narrow wording — lane 1's oracle is **analytic ground truth**, which is untouched, and bare `mujoco` and `pybullet` still run as independent arms. What is gone is the ability to run one `.wbt` through two integrations and diff. Lane 1's generator also emitted an `ode_pin` per scene, so the lane cannot be run exactly as designed. Frozen values survive in [`tests/goldens/ode_oracle_goldens.json`](../../tests/goldens/ode_oracle_goldens.json) — a golden file, not an oracle: it detects that Newton *changed*, it cannot adjudicate which engine was right. Several other goldens, control arms and frozen fixtures died the same way (the damage golden `husky_head_on_ode.wbt`, AgentBench Phase W's four `defaultPhysicsBackend "ode"` fixtures, lane 1's `t*_odepin` worlds).
> 2. **ODE was removed while its INTEGRATION still scored better on lane 1, and while it was the faster single-world backend.** ⚠️ Read that precisely: `omnisim-ode` outscored `omnisim-newton`, which compares two integrations — **not** two solvers. Bare MuJoCo scored fine on the same scenes, and the four defects behind Newton's deficit were in our own scene-graph-to-solver plumbing and were fixed in `e7b9fb11`. So do **not** say "ODE was more accurate than MuJoCo" (never measured), and equally do not let "ODE was a legacy tier" creep back in. Retirement was a capability, maintenance and licensing decision; the per-step cost advantage was real and is history. Full scope: [../benchmarks/correctness-scope.md](../benchmarks/correctness-scope.md).
> 3. **⚠ A load-only sweep cannot see wrong physics.** The campaign's sharpest lesson: `tests/api` scored **140/140 PASS** while all 140 of those worlds were `NUE` and had gravity projected to **exactly zero** — nothing in them ever fell. Post-fix (`c77cbe98`) the honest score is **128/139**. Wherever a doc here leans on a load-and-step PASS as *physics* evidence, distrust the framing. `run-headless --fail-on-runaway` exists for exactly this reason.
>
> Full record, the six kernel blockers and their outcomes, and the open defects the deletion left behind (motorised Ball/Hinge2 do not actuate; force-`TouchSensor` reads 0 N; contact sound and the contact-points GUI overlay are dead): **[ode-retirement-campaign.md](ode-retirement-campaign.md)**.

- **[OmniBench](../../tests/benchmarks/omnibench/) — *"how do I benchmark this?"* and *"what are our measured numbers?"* both end here.** The repo's runnable cross-simulator physics benchmark: three lanes (correctness against analytic ground truth, throughput to the post-Genesis credibility checklist, and determinism / train==deploy parity / agent-driveability), four engines as of its first campaign (MuJoCo 3.8.1, PyBullet, OmniSim/ODE, OmniSim/Newton — **ODE deleted 2026-08-08, so three now**), a machine fingerprint on every row, and one command to reproduce: `python tests/benchmarks/omnibench/run_all.py`. First campaign, two machines: [../benchmarks/omnibench-2026-07-24.md](../benchmarks/omnibench-2026-07-24.md). **Quote OmniSim numbers from there, with the machine id attached** — it supersedes the ad-hoc 2026-06-14 probes wherever they disagree (see the header box of [../benchmarks/performance-comparison.md](../benchmarks/performance-comparison.md)). Two results worth knowing before you write anything comparative: `omnisim-ode` **was** the best-scoring *integration* in lane 1 (⚠️ not a solver result — bare MuJoCo scored fine on the same scenes and the deficit was in our own plumbing, fixed in `e7b9fb11`; [../benchmarks/correctness-scope.md](../benchmarks/correctness-scope.md)), and cheaper per step than Newton at every scene size measured — Newton's win is *batching* — and the suite found five real Newton-integration bugs, all fixed (`e7b9fb11`) and cross-machine validated. ⚠ **Both ODE facts are now historical and unrepeatable** (`bdc02139`): lane 1 has lost its oracle, and the honest form of the batching claim — K-world Newton against K sequential ODE runs — is no longer buildable. Never quote a Newton-vs-ODE ratio as current.
- [../benchmarks/lane4-capability-matrix.md](../benchmarks/lane4-capability-matrix.md): **⚠️ READ THIS BEFORE TELLING ANYONE WHAT OMNISIM CAN SIMULATE — it is generated from measurements and it overrides the prose, including AGENTS.md.** OmniBench **lane 4** ([`tests/benchmarks/omnibench/lane4/`](../../tests/benchmarks/omnibench/lane4/README.md)) executes one probe per capability — object primitives, joints and actuation modes, devices, world-level contracts — each with a committed `.wbt` and an assertion in physical units, plus a per-machine scaling envelope and a CPU-only (no-CUDA-visible) probe. Its verdicts are `works` / `degraded` / **`broken`** / `absent`, and `broken` is the one nothing else in the suite can see: present in the schema, accepted at load, measurably doing nothing — **exactly what a bare `run-headless` PASS reports as success.** The lane also audits the documentation against itself and raises a finding when the two disagree in **either** direction. Two rules bind anyone reading it: a `broken` verdict is not publishable until it has been chased to a mechanism (most of the lane's early findings were its own calibration errors), and an instrument that never fired has not been shown to work — the constraint-overflow detector currently reports `cliff_detector_validated: false` and its silence must not be read as a pass.
- [../benchmarks/determinism-scope.md](../benchmarks/determinism-scope.md): **⚠️ READ THIS BEFORE WRITING ANY DETERMINISM OR REPRODUCIBILITY CLAIM — it is the source of truth and it overrides every other doc.** What OmniSim actually reproduces run-to-run, per configuration: **bitwise** on `newtonSolver "mujoco"` (CPU `mj_step`, verified at 336 contacts with ten live controllers) — the only live row; **bitwise** on ODE and on Newton/XPBD in the historical record, both now **unverifiable** because those configurations were deleted (`bdc02139`, `94f04222`), which also means the CPU-bitwise result has lost its independent corroborating backend; **refuted** on the GPU `newtonSolver "mujoco_warp"` path (0 bitwise of 24 same-config cold pairs, 9.152 m apart by 1000 steps, mechanism traced to `wp.atomic_add` contact-slot claiming); **untested** cross-machine. Also carries the false positive that briefly inflated the claim (a recorder that skipped undeffed nodes graded a stationary sun marker as bitwise) and the rule it cost us twice: *an assertion that has never gone red should be assumed broken until you make it go red on purpose.*
- [agent-native-api.md](agent-native-api.md): **our agent surface measured against the ROS 2 [`simulation_interfaces`](https://github.com/ros-simulation/simulation_interfaces) standard, adversarially.** 21 services scored 6 ahead / 5 partial / 10 missing, every latency measured on one machine in one session. Its update banner records what shipped since (`GET /capabilities`, `/scene/spawn|delete|set_pose`, `/sim/snapshot|restore`, a repaired `/sim/reset`, `POST /world/load {"light": true}`) **and the three proposals that turned out to be wrong** — a `URDFRobot` cannot be spawned from a node string (clone instead), the snapshot risk was the zero-vector default not the pose re-sync, and the flagship before/after table overstated the win as wall time. Read before adding a harness verb.
- [agent-edge-validation-plan.md](agent-edge-validation-plan.md): **⚠️ "do agents actually get more done here?" — the programme, written BEFORE the runs so the retreat cannot be improvised.** On 2026-07-26 the first A/B of our own agent surface against a bare POSIX shell had **the shell win or tie every run**, so the claim that an agent gets more done on OmniSim is **currently unsupported by any measurement we hold**. Nothing in the file is a result. The contract it implements is [`tests/benchmarks/agentbench/SPEC.md`](../../tests/benchmarks/agentbench/SPEC.md).
- [ladder-findings-2026-08-02.md](ladder-findings-2026-08-02.md): **what the capability ladder's first real agent cell found out about THIS product** — findings on the record, none of them fixed. (a) `omnilink_arm_bridge`'s grasp is a **kinematic weld** (`_attach_nearest` + a per-tick `setSFVec3f(tcp)` teleport) while three comments and a shipped world header claim contact friction — the honest no-weld pinch of the same block holds **1.376 s against a 10 s target**; (b) `WorldInfo.contactProperties` (`coulombFriction`, `softCFM`, …) is read **only** by the ODE path (`OmSimulationCluster.cpp:240`) and is **inert under the default Newton backend**, which pins `mu = 1.0` — ⚠ **and since `bdc02139` deleted that reader, these fields are now read by *nothing on any path*, which makes the finding strictly worse rather than resolved** — proven independently by four softCFM configs returning bit-identical numbers across 300×, and **322** `.wbt` files in this tree declare the field; (c) the pattern, cross-referenced with the contact blindness (1008 contacts on ODE vs **0** on Newton) and the missing wrench read-back: **the default backend accepts, validates and then silently ignores several things a world file declares.** The cell itself was INVALID for instrument reasons and says so.
- [webots-control-baseline.md](webots-control-baseline.md): **how to stand up upstream Webots R2025a as the CONTROL arm** of that programme (Phase W) — same file format, same base engine, no harness. If an agent does as well on plain Webots, everything we built on top buys nothing. The cheapest decisive experiment we have, and the harshest; includes the traps that would otherwise invalidate the comparison.
- [`tests/benchmarks/omnilink_long_horizon/SPEC.md`](../../tests/benchmarks/omnilink_long_horizon/SPEC.md): the **long-horizon** lane — one natural-language objective to Mission Captain, which must inspect its roster, delegate a self-contained mission to Husky Maze, and close only against a completed delegation ledger. - [ros2-integration.md](ros2-integration.md): ⭐ **the ROS 2 story — a non-goal until 2026-08-17, now a shipped sidecar.** OmniSim implements the ROS 2 `simulation_interfaces` standard (v2.1.0) plus `/clock`, `/tf`, `JointState`, `/odom` and `cmd_vel`, as [`packages/omnisim-ros2/`](../../packages/omnisim-ros2/) — with **the engine still ROS-free** (no `rclcpp` in `src/omnisim/`, no ROS in the engine Makefiles). The MCP front door to the same HTTP surface is [`packages/omnisim-mcp/`](../../packages/omnisim-mcp/).

## Robot Learning & Motion

**Read in this order.** ⭐ **[shadowing.md](shadowing.md)** is the FLAGSHIP method; **[rl-current-state.md](rl-current-state.md)** is the CANONICAL status (never quote a result from any other doc).

- [shadowing.md](shadowing.md): ⭐ **SHADOWING — the flagship algorithm for legged-robot motion (maintainer directive 2026-07-03). READ THIS FIRST for any new motion-control / imitation effort.** Train in-engine (train == deploy bit-exact) to shadow a **ghost** (a dynamically-feasible reference) via **corridors** + **WBMATCH** + **GHOST-MORPH**. The thesis: *ghost feasibility, not RL tuning, is the bottleneck* — so verify the reference **before** you learn. Implementation: [`projects/policies/training/`](../../projects/policies/training/README.md). Training is **in-engine and LOCAL** — there is no cloud path.
- [ghost-design-rules.md](ghost-design-rules.md): ⭐ **the ghost doctrine — the FOUR GATES + the CORRIDOR-vs-TORQUE LAW + the 7 design rules, and the ghost toolchain.** Gates 1–3 (closure / support / FWP) are static; **gate 4** (`ghost_funnel.py`) asks whether a deploy-grade PD plant can actually *track* the reference. The LAW: **a tracking corridor must exceed `τ_ff/kp`, or the reference is untrackable BY CONSTRUCTION** — it retro-explains every corridored run that failed. Run [`ghost_validator.py`](../../projects/policies/training/ghost_validator.py) on ANY new ghost **before** training.
- [skill-library.md](skill-library.md): **the SKILL LIBRARY — the standard way to make a skill and compose skills.** Wraps Shadowing + BATON into one pipeline (design → validate → preview → train → verify → register → sequence); a *skill* (walk / turn / carry / stand / climb, + H1 / Go2 / OmniQuad) is one versioned manifest binding its ghost + validator verdict + deploy env + champion checkpoint + provenance. Front door: `projects/policies/skills/skill_lib.py` (`list`/`sequence`/`preview`/`train`/`verify-demos` + `handover`/`blendable`/`adapt`/`freeze`). **Start here to add a new skill or build a BATON demo.**
- [policy-switching.md](policy-switching.md): **BATON — runtime handover between separately-trained Shadowing specialists** (walk / stand / carry / turn). The handover machinery ships and is live-verified (four sequences: `box_delivery`, `box_delivery_classic`, `walk_turn_walk`, `turn_solo`; the 90° footwork turn is SOLVED, `72a7bb19`). ⚠️ The *switching-beats-a-monolith* **thesis remains an open hypothesis** — the success-vs-horizon experiment is unrun. Read its "Where BATON stands vs the field" section before making any novelty claim.

## Scope

These docs are intentionally pragmatic:

- they describe the codebase as it exists now
- they call out the fast paths that are actually available today
- they note where a path is a wrapper over legacy makefiles rather than a fully modular system

When the code and docs disagree, update the docs in the same change.
